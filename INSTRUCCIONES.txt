## 1. Módulo Login / Credenciales — backend/server.js

**Líneas mal:** 11-14 (secretos hardcodeados)

**Reemplazar:**
```javascript
const ADMIN_USER = 'admin@tienda.com';
const ADMIN_PASSWORD = 'Admin123!';
const STRIPE_SECRET_KEY = 'sk_live_abc123xyz789secreto';
const DB_PASSWORD = 'root123';
```

**Por:**
```javascript
const ADMIN_USER = process.env.ADMIN_USER || '';
const ADMIN_PASSWORD = process.env.ADMIN_PASSWORD || '';
const STRIPE_SECRET_KEY = process.env.STRIPE_SECRET_KEY || '';
const DB_PASSWORD = process.env.DB_PASSWORD || '';
```

## 2. Módulo Búsqueda de usuario (SQL Injection) — backend/server.js

**Línea mal:** 41 (concatenación en la consulta SQL)

**Reemplazar:**
```javascript
const querySimulada = "SELECT * FROM usuarios WHERE email = '" + email + "'";
```

**Por:** no concatenar la entrada del usuario. Dentro de `buscarUsuarioPorEmail` devolver solo el email sanitizado, por ejemplo:
```javascript
return { email: String(email).slice(0, 255) };
```
(Eliminar la variable `querySimulada` y cualquier uso de concatenación con `email` en una query.)

**Línea mal:** 47 (entrada sin limitar)

**Reemplazar:**
```javascript
const email = req.query.email || '';
```

**Por:**
```javascript
const email = (req.query.email || '').toString().slice(0, 255);
```

## 3. Módulo Registro — backend/server.js

**Líneas mal:** 53-62 (sin validación de email, contraseña ni longitudes)

**Reemplazar:** todo el bloque de `app.post('/api/registro', ...)` que usa directo `nombre`, `email`, `password` del body.

**Por:** validar y limitar antes de usar:
```javascript
app.post('/api/registro', (req, res) => {
  const { nombre, email, password } = req.body;
  const nombreSafe = (nombre && String(nombre).trim().slice(0, 100)) || '';
  const emailSafe = (email && String(email).trim().slice(0, 254)) || '';
  if (!emailSafe || !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(emailSafe)) {
    return res.status(400).json({ message: 'Email inválido' });
  }
  if (!password || password.length < 8) {
    return res.status(400).json({ message: 'Contraseña debe tener al menos 8 caracteres' });
  }
  usuarios.push({
    id: usuarios.length + 1,
    nombre: nombreSafe,
    email: emailSafe,
    passwordHash: 'hash_' + password
  });
  res.json({ ok: true, message: 'Usuario registrado' });
});
```

## 4. Módulo Carrito (eval) — backend/server.js

**Líneas mal:** 65-70 (uso de `eval` con datos del usuario)

**Reemplazar:**
```javascript
app.post('/api/carrito/parsear', (req, res) => {
  const { datos } = req.body;
  let items;
  items = eval('(' + datos + ')');
  if (!Array.isArray(items)) items = [];
  res.json({ items, total: items.length });
});
```

**Por:**
```javascript
app.post('/api/carrito/parsear', (req, res) => {
  const { datos } = req.body;
  if (typeof datos !== 'string') {
    return res.status(400).json({ error: 'Datos debe ser string JSON' });
  }
  let items;
  try {
    items = JSON.parse(datos);
    if (!Array.isArray(items)) items = [];
  } catch (e) {
    return res.status(400).json({ error: 'JSON inválido' });
  }
  res.json({ items, total: items.length });
});
```

## 5. Módulo Login (frontend) — frontend/LoginVulnerable.js

**Línea mal:** 8 (contraseña en el cliente)

**Reemplazar:**
```javascript
const DEFAULT_ADMIN_PASS = 'admin123';
```

**Por:** eliminar esa constante. No debe haber contraseñas ni secretos en el frontend.

**Líneas mal:** 16-19 (comparación con contraseña en el cliente)

**Reemplazar:** la lógica que compara `password === DEFAULT_ADMIN_PASS` y redirige.

**Por:** enviar email y contraseña al backend (por ejemplo `POST /api/login`) y, según la respuesta, redirigir o mostrar error. La validación debe hacerse solo en el servidor.

## 6. Módulo Carrito (XSS) — frontend/CarritoVulnerable.js

**Línea mal:** 25 (HTML sin sanitizar desde entrada del usuario)

**Reemplazar:**
```javascript
<div dangerouslySetInnerHTML={mostrarComentario()} />
```

**Por:**
```javascript
<div>{comentario}</div>
```

Opcional: eliminar la función `mostrarComentario` si ya no se usa.

## 7. Módulo CSRF — backend/server.js

**Qué marca Semgrep:** no se detecta middleware CSRF en la aplicación Express (regla `express-check-csurf-middleware-usage`).

**Dónde corregir:** al inicio del archivo, después de `app.use(express.json());`.

**Añadir:** los requires y el uso del middleware:

```javascript
const cookieParser = require('cookie-parser');
const csurf = require('csurf');
```

(junto a `const express = require('express');`)

y después de `app.use(express.json());`:

```javascript
app.use(cookieParser());
app.use(csurf({ cookie: true }));
```

Las dependencias `cookie-parser` y `csurf` ya están en `package.json`; si no, instala con `npm install cookie-parser csurf`. Referencia de código corregido: `backend/server-seguro.js` (ahí ya está aplicado).

## Una vez corregido, ¿cómo sé que ya está? ¿Que esto funciona?

### 1. Saber que las vulnerabilidades ya no están (SAST)

Usa siempre el mismo comando (CSRF ya está corregido en el código con el middleware en ambos servidores):

```powershell
cd "C:\Users\Miguel Angel\practica-sast"
semgrep scan --config auto .
```

- **Primer escaneo (código vulnerable):** se analiza todo; los hallazgos salen en `backend/server.js` y en el frontend.
- **Segundo escaneo (para ver 0 hallazgos):** como `server.js` lo dejas vulnerable a propósito, escanea solo la versión segura y el frontend:
```powershell
semgrep scan --config auto backend/server-seguro.js frontend/
```
Así el reporte solo incluye el código corregido y debería salir sin hallazgos.

- **Antes de corregir:** Semgrep mostraba varios hallazgos (secretos, eval, SQL injection, XSS, etc.).
- **Después de corregir:** Esos mismos hallazgos **no deberían aparecer** (o serán muchos menos). Si la lista de resultados es vacía o ya no sale nada en `backend/server.js`, `LoginVulnerable.js` ni `CarritoVulnerable.js` para esas reglas, **ya está corregido** desde el punto de vista SAST.

En la práctica: “corregido” = segundo escaneo sin (o con menos) hallazgos en esos archivos.

### 2. Saber que la aplicación sigue funcionando

Para comprobar que el backend no se rompió con los cambios:

1. En la carpeta `backend` instala dependencias (solo la primera vez):
   ```powershell
   cd backend
   npm install
   ```

2. Arranca el servidor:
   - **Versión vulnerable** (server.js, no lo borres): `node server.js` o `npm start`
   - **Versión corregida** (sin tocar server.js): `node server-seguro.js` o `npm run start:seguro`

3. Con el servidor en marcha, prueba desde el navegador o con una herramienta como Postman/Insomnia:
   - **Login:** `POST http://localhost:3001/api/login` con body `{ "email": "admin@tienda.com", "password": "Admin123!" }` (o las credenciales que tengas en `.env` si usas variables de entorno).
   - **Registro:** `POST http://localhost:3001/api/registro` con `{ "nombre": "Test", "email": "test@test.com", "password": "12345678" }`.
   - **Carrito:** `POST http://localhost:3001/api/carrito/parsear` con `{ "datos": "[{\"id\":1,\"nombre\":\"Producto\"}]" }`.

Si obtienes respuestas JSON (token, “Usuario registrado”, lista de items) y no errores 500, **la aplicación funciona** después de las correcciones.

**Resumen:** “Ya está” = segundo escaneo Semgrep sin esos hallazgos. “Funciona” = servidor arranca y los endpoints responden bien.
